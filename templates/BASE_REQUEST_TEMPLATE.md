# LOOKDO — BASE REQUEST TEMPLATE

Этот документ описывает **неизменяемое ядро всех шаблонов заявок** LOOKDO.

Конкретные виды бизнеса не получают собственные экраны. Они получают только конфигурацию этого базового шаблона.

## 1. Неизменяемый пользовательский flow

Для всех профессий порядок одинаков:

1. Пользователь открывает центральное действие.
2. Видит короткий заголовок и подсказку.
3. Добавляет фото и, если разрешено шаблоном, короткое видео.
4. Заполняет только несколько дополнительных универсальных полей.
5. При желании пишет свободный комментарий.
6. Вводит **обязательный номер телефона**.
7. Отправляет заявку.
8. Получает экран успешной отправки с номером заявки.
9. Ему предлагается включить push-уведомления.
10. После ответа бизнеса пользователь продолжает переписку в общем экране Messages.

Этот flow не меняется между профессиями.

---

## 2. Неизменяемые части UI

Не меняются:

- общий layout экрана заявки;
- верхняя навигация;
- нижняя навигация;
- расположение media uploader;
- preview фото/видео;
- delete/re-take actions;
- блок дополнительных полей;
- блок комментария;
- блок телефона;
- submit area;
- экран «Заявка отправлена»;
- push pre-prompt;
- Messages;
- Contacts;
- Reviews;
- общая логика ошибок/валидации.

UI должен соответствовать утверждённым макетам из `/UI`.

---

## 3. Неизменяемая структура данных заявки

Основная таблица должна оставаться универсальной:

```text
requests
- id
- tenant_id
- template_id
- customer_name nullable
- customer_phone
- comment nullable
- status
- preferred_reply_channel nullable
- created_at
- updated_at
```

Значения дополнительных полей не добавлять отдельными колонками под каждую профессию.

Использовать универсальную структуру:

```text
request_field_values
- id
- request_id
- field_key
- value_text nullable
- value_number nullable
- value_boolean nullable
- value_json nullable
```

Медиа также универсальны:

```text
media
- id
- tenant_id
- request_id nullable
- type (image/video)
- role
- slot_key nullable
- sort_order
- storage_key
- mime_type
- size_bytes
- metadata_json nullable
- created_at
```

Не создавать `car_requests`, `door_requests`, `washing_machine_requests` и подобные специализированные таблицы.

---

## 4. Универсальные типы дополнительных полей

В v1 разрешены только простые типы:

- `text`
- `textarea`
- `select`
- `number`
- `checkbox`

При необходимости можно добавить позже другие универсальные типы централизованно.

Каждое поле шаблона описывается конфигурацией:

```json
{
  "key": "model",
  "type": "text",
  "label": "Марка и модель",
  "placeholder": "Например, BMW X5",
  "required": false,
  "sort_order": 10
}
```

Никаких специализированных Vue-компонентов `CarModelField`, `DoorWidthField`, `WasherBrandField` без реальной необходимости.

---

## 5. Универсальная модель media slots

Шаблон может изменить только смысл и подсказку photo/video slots.

Пример:

```json
{
  "key": "overall",
  "type": "image",
  "label": "Общий вид",
  "hint": "Сфотографируйте объект целиком",
  "required": true,
  "max_files": 1,
  "sort_order": 10
}
```

Другой шаблон может использовать тот же slot engine с текстом «Фото шильдика» или «Повреждение крупным планом».

Общий uploader и backend остаются теми же.

---

## 6. Что конкретный шаблон имеет право менять

Только конфигурацию:

- `code`;
- название шаблона;
- category;
- primary action label;
- заголовок;
- короткое intro;
- media slots и их тексты;
- min/max photo count;
- `video_allowed`;
- video hint;
- дополнительные универсальные fields;
- label/placeholder комментария;
- submit button text;
- success text;
- локализации;
- AI phrases/synonyms.

## 7. Что конкретный шаблон НЕ имеет права менять

Шаблон не может:

- добавлять новый публичный экран;
- менять общий navigation model;
- создавать свой uploader;
- создавать отдельную систему сообщений;
- создавать отдельную систему push;
- создавать отдельную таблицу заявки;
- менять обязательность `customer_phone`;
- рассчитывать обязательную цену;
- создавать собственную authentication logic.

---

## 8. Телефон — неизменяемое обязательное поле

`customer_phone` обязателен для всех шаблонов.

Причина: push, browser session или встроенный чат не являются достаточной гарантией связи с клиентом.

E-mail конечного клиента по умолчанию не запрашивается.

---

## 9. Комментарий

Свободный комментарий доступен во всех шаблонах, но его label/placeholder может меняться.

Примеры:

- «Что хотите изменить?»
- «Опишите неисправность»
- «Что требуется установить?»

Само поле и storage остаются общими.

---

## 10. Видео

Видео не создаёт отдельный flow.

Шаблон только устанавливает:

- `video_allowed: true/false`;
- optional hint;
- plan-dependent max duration/size.

Например для шумящей бытовой техники видео особенно полезно, а для установки двери обычно не требуется.

---

## 11. Backend API

Должен быть общий API для всех шаблонов, например концептуально:

```text
GET  /api/public/template
POST /api/public/requests
POST /api/public/requests/{request}/media
GET  /api/public/requests/{request}/conversation
POST /api/public/requests/{request}/messages
```

Не создавать `/api/car-requests`, `/api/door-installations` и подобные endpoint.

---

## 12. Runtime загрузка шаблона

Frontend не должен искать логику профессии по разным файлам.

После tenant resolution backend возвращает активный request template tenant одним объектом.

Vue `RequestScreen`/template engine строит экран по этой конфигурации.

Концептуальный ответ:

```json
{
  "template_code": "automotive-steering-wheel",
  "primary_action_label": "Оценить мой руль",
  "title": "Покажите ваш руль",
  "intro": "Сделайте несколько фотографий, чтобы мастер мог посмотреть состояние.",
  "media_slots": [],
  "fields": [],
  "comment": {},
  "phone": {
    "required": true
  },
  "submit_text": "Отправить Леониду"
}
```

Конкретное имя мастера в button text должно приходить из tenant content/config, а не hardcode в шаблоне.

---

## 13. Super Admin — редактор шаблонов

Все конкретные шаблоны должны быть видимы и редактируемы централизованно в Super Admin.

Нужно уметь:

- создать шаблон;
- клонировать существующий;
- изменить category;
- настроить media slots;
- добавить/удалить дополнительные поля;
- редактировать тексты и локализации;
- включить/выключить video;
- добавить AI phrases;
- preview шаблона;
- disable шаблон без удаления;
- version/change log минимум на уровне audit log.

Создание нового шаблона должно быть операцией с данными, а не новой разработкой frontend.

---

## 14. Support fallback

В onboarding и выборе шаблона обязательно показывать:

**Не нашли подходящий шаблон? Напишите в поддержку — мы посмотрим и добавим.**

Пользователь не создаёт произвольный workflow сам в v1.

Support-запрос должен сохранять:

- tenant/user;
- введённое описание деятельности;
- варианты, которые предлагал AI;
- комментарий пользователя.

Так библиотека LOOKDO постепенно расширяется на основе реальных запросов.

---

## 15. Критерий правильной реализации

Новый бизнес-шаблон считается корректно спроектированным, если его можно добавить путем:

1. клонирования существующей конфигурации;
2. изменения текстов/media slots/universal fields;
3. добавления AI phrases;
4. сохранения в БД;
5. без изменения Vue screens, routes, API и database schema.

Это главный архитектурный принцип Template Engine LOOKDO.
