# 1. Что такое LOOKDO

LOOKDO — SaaS-платформа, с помощью которой малый сервисный бизнес получает собственное брендированное мобильное Web App/PWA на своём домене.

Главная идея продукта:

> **LOOK. DO.**  
> **СМОТРИ. ДЕЛАЙ.**

Клиент бизнеса показывает задачу фотографией или коротким видео. Специалист смотрит и отвечает. Не нужно заставлять клиента разбираться в профессиональных терминах и заполнять длинные формы.

LOOKDO не позиционировать как обычный конструктор сайтов.

Ключевое отличие:

**Обычный сайт только показывает информацию. LOOKDO позволяет посетителю сразу показать бизнесу свою задачу.**

# 7. AI-классификация при onboarding

AI — обязательная часть продукта уже на первом этапе.

Пользователь пишет деятельность свободным текстом.

Примеры:

- «перетягиваю автомобильные рули»;
- «занимаюсь установкой дверей»;
- «ремонтирую стиральные машины»;
- «перетягиваю диваны».

Алгоритм:

1. normalize input;
2. exact match по словарю;
3. fuzzy/semantic search по `business_phrases`;
4. shortlist лучших фиксированных вариантов;
5. AI получает исходную фразу + shortlist;
6. AI выбирает только `category_id + variation_id`;
7. сохраняется confidence/source;
8. если confidence низкий — показать пользователю 2–3 варианта.

AI не имеет права создавать новые категории или сценарии.

Подробная таксономия и полный словарь находятся в основном `CODEX.md` и должны использоваться как seed/source данных.

# 8. Тарифы — единый источник истины

Тарифы НЕ должны быть захардкожены отдельно на публичной странице.

Источник истины:

`plans + plan_features/entitlements` в backend.

Один и тот же тариф используется:

- публичной страницей `/pricing`;
- регистрацией;
- checkout;
- Tenant Admin;
- Super Admin;
- feature gating;
- лимитами.

## 8.1 Модель тарифа

Минимально хранить:

```text
plans
- id
- code
- name
- description
- price_monthly
- price_yearly
- currency
- trial_days
- is_active
- is_public
- sort_order
- badge_text
- created_at
- updated_at
```

Права/лимиты отдельно:

```text
plan_entitlements
- id
- plan_id
- key
- value
```

Примеры `key`:

- storage_mb
- video_enabled
- video_max_mb
- video_max_seconds
- custom_domain
- staff_users
- telegram_integration
- vk_integration
- branding_colors
- platform_branding_removable
- requests_history_days
- push_enabled

Не разбрасывать проверки плана по Vue-компонентам. Использовать единый backend entitlement service/API.

## 8.2 Публичная страница тарифов

Показывает только `is_public && is_active`.

Карточка:

- название;
- короткое назначение;
- месячная цена;
- годовая цена/экономия, если используется;
- ключевые возможности;
- лимиты, только если важны клиенту;
- CTA.

Поддержать highlight/recommended plan через данные backend.

**Конкретные коммерческие цены пока не фиксировать в коде как неизменяемые. Все цены редактируются Super Admin.**

## 8.3 Бесплатный/индивидуальный доступ

Super Admin должен уметь:

- назначить tenant любой plan;
- задать 100% скидку/complimentary subscription;
- сделать бессрочный бесплатный доступ;
- переопределить отдельные entitlements для конкретного tenant.

Это позволяет, например, дать полноценный тариф первому клиенту бесплатно без специального кода.

# 17. Что НЕ делать в Части 1

До отдельного подтверждения перехода к Части 2 **не реализовывать**:

- рабочую камеру конечного клиента;
- отправку заявок клиента мастеру;
- клиентские сообщения;
- клиентские push по заявке;
- публичные отзывы tenant;
- полноценный Before/After manager;
- рабочий Telegram bot заявок;
- рабочий VK flow заявок;
- полноценный Capacitor Android build;
- сложную CRM;
- календарь;
- калькулятор цены;
- marketplace;
- e-commerce/catalog/cart.

При этом архитектура Части 1 не должна мешать этим функциям в Части 2.

# 18. Definition of Done — Часть 1

Часть 1 считается готовой только когда:

1. `lookdo.app` имеет полноценную локализованную SaaS-главную.
2. Есть страница тарифов из backend данных.
3. Новый пользователь может зарегистрироваться.
4. Работает вход/выход/восстановление доступа.
5. Onboarding спрашивает деятельность.
6. Словарь + AI возвращают существующую category + variation.
7. При низкой уверенности пользователь подтверждает вариант.
8. Создаётся отдельный tenant.
9. Tenant видит свой кабинет.
10. Tenant может видеть тариф/подписку.
11. Tenant может добавить собственный домен и получить DNS-инструкцию.
12. Super Admin видит и управляет tenant.
13. Super Admin создаёт/редактирует тарифы и entitlements.
14. Изменения тарифов автоматически видны на публичной Pricing page.
15. Super Admin может назначить бесплатный/complimentary доступ.
16. Super Admin управляет taxonomy и словарём AI-фраз.
17. Есть AI classification log.
18. Работают DE/EN/RU.
19. Admin areas защищены и noindex.
20. Основные admin actions имеют audit log.

**После этого остановиться. Не начинать Часть 2 автоматически.**

Следующий отдельный этап после проверки владельцем проекта: **Часть 2 — клиентское Web App/PWA конкретного tenant.**
