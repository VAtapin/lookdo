# LOOKDO — полное техническое задание для Codex

> **LOOK. DO.**  
> **СМОТРИ. ДЕЛАЙ.**

## 1. Суть продукта

LOOKDO — мультитенантная SaaS-платформа для сервисного бизнеса, мастерских и других видов деятельности, где клиент может **показать задачу** фотографиями или коротким видео, а реальный специалист посмотрит материалы, ответит и договорится с клиентом о работе.

Ключевой принцип продукта: **не заставлять клиента разбираться в профессиональных терминах и заполнять длинные формы. Покажи задачу — мастер посмотрит.**

Типовой путь конечного клиента:

1. Открыть брендированное приложение конкретного бизнеса.
2. Увидеть, чем занимается мастер/компания, примеры «До/После», видео и отзывы.
3. Нажать центральное действие: например «Оценить мой руль», «Показать повреждение», «Показать объект».
4. Сделать или загрузить фотографии/короткое видео.
5. Ответить только на минимальные вопросы, необходимые выбранному шаблону.
6. Ввести **обязательный номер телефона**.
7. Отправить заявку.
8. При желании включить push-уведомления.
9. Получить ответ мастера и продолжить переписку в приложении либо связаться по доступному внешнему каналу.

LOOKDO — не классический конструктор сайтов, не тяжёлая CRM, не маркетплейс и не онлайн-калькулятор цены.

**Автоматически рассчитывать обязательную цену нельзя.** У реальной работы почти всегда есть нюансы; предложение делает мастер после просмотра заявки.

## 2. Зафиксированный стек

- **Backend:** Laravel API
- **Frontend:** Vue 3
- **Build:** Vite
- **Web App:** PWA
- **Native-ready:** Capacitor-ready с самого начала
- **Database:** MariaDB/MySQL-compatible
- **Queue:** Laravel Queues
- **Cache/session:** Redis-ready
- **Storage:** Laravel Filesystem; local + S3-compatible

Frontend и backend разделять через API-контракты. Не строить Blade-first приложение с последующей переделкой на Vue.

Камеру, push, файлы, sharing и другие возможности устройства оборачивать в отдельные frontend services/adapters, чтобы web-реализацию позднее можно было заменить/дополнить Capacitor-плагинами без переписывания UI.

## 3. SaaS и мультитенантность

LOOKDO строится как SaaS **с первого коммита**.

Каждый бизнес — `tenant`.

Tenant имеет собственные:

- название и профиль;
- логотип;
- фирменные цвета;
- hero-фото/hero-видео;
- домены;
- пользователей/сотрудников;
- направление деятельности и выбранный шаблон;
- заявки;
- сообщения;
- фотографии и видео;
- пары «До/После»;
- отзывы;
- контакты и часы работы;
- языки;
- уведомления;
- интеграции;
- тариф/подписку;
- лимиты/entitlements.

Все tenant-owned записи обязательно tenant-scoped. Утечка данных между tenant недопустима.

Tenant определяется по hostname/domain. Предусмотреть платформенный preview/subdomain fallback.

### Первый реальный tenant

Мастерская Леонида по перетяжке автомобильных рулей — первый tenant.

**Никакого Leonid-specific кода.** Леонид — обычный клиент SaaS. Через Super Admin ему можно назначить полноценный тариф бесплатно/бессрочно.

## 4. Домены

Основной домен платформы: **lookdo.app**.

Клиент SaaS самостоятельно регистрирует собственный домен и направляет DNS на сервер LOOKDO.

Поток:

1. Tenant вводит свой домен.
2. LOOKDO показывает DNS-инструкцию.
3. Клиент меняет DNS у регистратора.
4. LOOKDO проверяет DNS.
5. Домен связывается с tenant.
6. Выпускается SSL.
7. Домен открывает публичное PWA этого tenant.

Статусы минимум:

- `pending`
- `dns_detected`
- `verifying`
- `active`
- `failed`

Посетитель собственного домена должен видеть бренд бизнеса, а не LOOKDO, если branding платформы специально не предусмотрен тарифом.

# 5. Жёсткое правило клиентского UI

LOOKDO — **app, а не сайт-портянка**.

Основная нижняя навигация конечного клиента всегда состоит максимум из трёх пунктов:

1. **Главная**
2. **Центральное действие**
3. **Сообщения**

Текст центрального действия задаётся шаблоном/tenant, например:

- Оценить мой руль
- Показать повреждение
- Показать объект
- Показать неисправность
- Показать мебель
- Показать изделие
- Отправить фото

**Новая профессия никогда не должна создавать новый публичный экран.**

Категории/вариации меняют только:

- текст основной кнопки;
- названия полей;
- видимость полей;
- обязательность полей;
- количество/тип фото;
- разрешение короткого видео;
- подсказки съёмки;
- стартовые тексты.

Отдельный постоянный раздел «Наши работы» в нижнем меню не нужен. «До/После» и лучшие работы показываются на Главной.

# 6. Публичные экраны и служебные состояния

## 6.1 Главная

Первый экран должен представлять бизнес и сразу создавать доверие.

Содержит:

- логотип/название бизнеса;
- hero-фото или короткое hero-видео;
- короткий заголовок;
- короткое описание;
- компактный блок **До/После**;
- лучшие работы без отдельной большой галереи;
- несколько преимуществ;
- компактное представление мастера/компании;
- превью отзывов;
- телефон/контакты;
- VK/Telegram при наличии интеграции;
- постоянную нижнюю навигацию.

Допустима небольшая прокрутка на маленьком телефоне, но экран не должен превращаться в классический длинный landing page.

## 6.2 Центральное действие / заявка

Поддержать:

- камеру телефона;
- выбор фото из галереи;
- обычно 1–4 фото, настраивается шаблоном;
- короткое видео, если разрешено;
- preview;
- удалить;
- переснять;
- минимальные поля шаблона;
- комментарий;
- **обязательный телефон клиента**;
- предпочтительный канал ответа.

E-mail клиента в стандартном потоке **не нужен**.

## 6.3 Камера / добавление фотографий

Это отдельное состояние существующего процесса, а не новый раздел приложения.

Шаблон может требовать/предлагать последовательность, например:

- общий вид;
- левая сторона;
- правая сторона;
- крупный план повреждения;
- шильдик/модель;
- место установки;
- пример/референс.

Поддержать:

- capture;
- gallery/file fallback;
- multiple upload;
- короткое видео;
- preview/delete/re-take;
- разумное client-side resize/compression;
- обязательную server-side MIME/size validation.

## 6.4 Заявка отправлена

Показывает:

- успешную отправку;
- номер заявки;
- краткое резюме;
- контакты бизнеса;
- предложение включить уведомления.

## 6.5 Push pre-prompt

Нельзя сразу при первом открытии сайта показывать системный browser prompt.

Сначала собственный экран/модальное состояние с понятным объяснением, например:

**«Разрешите уведомления, и мы сообщим, когда мастер ответит.»**

Только после нажатия пользователем вызывается browser permission request.

Сервисные push и рекламное согласие хранить раздельно. Маркетинг — только при отдельном согласии.

## 6.6 Сообщения

Простой чат клиента с бизнесом, привязанный к заявке.

Поддержать:

- сообщения обеих сторон;
- фотографии/вложения;
- время;
- контекст заявки;
- unread counter;
- push deep link прямо в нужный разговор.

Не строить социальный мессенджер.

## 6.7 Отзывы

Отзывы нужны как полноценная функция.

Поддержать:

- средний рейтинг;
- число отзывов;
- звёзды;
- текст;
- фото;
- короткое видео;
- ответ бизнеса;
- публикацию/скрытие;
- featured reviews на Главной;
- связь с завершённой заявкой, где возможно.

После завершения работы можно отправить сервисный push с просьбой оставить отзыв.

## 6.8 Контакты

Не отдельный основной раздел, а bottom sheet/modal:

- позвонить;
- VK;
- Telegram, если включён;
- адрес;
- маршрут;
- часы работы.

# 8. Админка tenant

Админка обязательна и должна быть удобна с телефона.

Разделы:

- Обзор
- Заявки
- Сообщения
- Контент
- Отзывы
- Профиль
- Интеграции
- Домен
- Тариф
- Настройки

## 8.1 Заявки

- новые заявки;
- обязательный телефон клиента;
- все фото/видео;
- данные шаблона;
- комментарий;
- ответ клиенту;
- позвонить;
- статусы;
- архив.

Минимальные статусы:

- `new`
- `in_progress`
- `answered`
- `completed`
- `archived`

Не раздувать это до CRM.

## 8.2 Профиль

Экран **Профиль нужен**.

Настройки:

- название бизнеса;
- логотип;
- фото владельца/мастера;
- описание;
- телефон;
- адрес;
- часы работы;
- VK/Telegram/другие ссылки;
- языки;
- уведомления;
- основные цвета.

## 8.3 Брендинг

За основу UI берётся разработанное направление: premium dark/mobile app UI. Но tenant должен менять основные цвета.

Минимум:

- primary/accent color;
- secondary/support color;
- logo;
- hero image/video.

**Не делать page builder и отдельный дизайн для каждой профессии.** Структура приложения фиксированная.

## 8.4 Фото/видео

Загрузка должна быть максимально удобной:

- drag & drop на desktop;
- камера/галерея на mobile;
- progress;
- reorder;
- delete;
- preview;
- crop/thumbnail там, где полезно;
- compression;
- video size/duration limits;
- MIME validation;
- poster/thumbnail strategy;
- background processing/transcoding-ready.

## 8.5 До/После

Нужен reusable touch-friendly **Before/After slider**.

В админке tenant создаёт:

- фото «до»;
- фото «после»;
- заголовок;
- короткую подпись, необязательно.

# 9. Уведомления

## Клиент

- мастер ответил;
- полезное изменение статуса;
- работа завершена;
- просьба оставить отзыв;
- маркетинг только с отдельным согласием.

## Tenant

- новая заявка;
- новое сообщение клиента;
- новый отзыв, опционально.

Каналы:

- Web Push/PWA;
- e-mail владельца tenant;
- VK;
- Telegram для рынков/tenant, где он используется.

Полная заявка с фото/ссылками и телефоном должна уметь приходить владельцу на его служебный e-mail. E-mail конечного клиента не требуется.

# 10. Telegram

Telegram bot — дополнительный интерфейс SaaS, прежде всего для рынков/клиентов, где Telegram используется. Он работает с тем же Laravel backend и не дублирует бизнес-логику.

Минимум:

- новая заявка;
- резюме заявки;
- фото/ссылки на медиа;
- новое сообщение клиента;
- ссылка в Tenant Admin;
- архитектурная возможность позже отвечать клиенту через bot.

# 11. VK

Для tenant, работающих с VK, предусмотреть интеграцию сообщества/контактов.

Не считать, что VK разрешает произвольно писать любому посетителю. Реализация должна учитывать актуальные разрешения API и факт взаимодействия/согласия пользователя.

**Телефон клиента остаётся обязательным надёжным контактом.**

# 12. Языки

Платформа localization-first.

Обязательные локали:

- `de` — немецкий;
- `en` — английский;
- `ru` — русский.

Не hardcode пользовательские строки в Vue.

Разделить:

1. переводы платформы;
2. tenant-editable тексты;
3. тексты/подсказки шаблонов;
4. словарь AI-классификации по языкам.

Tenant включает нужные языки публичного приложения.

# 13. Регистрация бизнеса и AI — обязательная часть продукта

AI должен быть встроен именно в onboarding и подбор логики заявки.

Пользователь **не обязан разбираться в наших категориях**.

При регистрации задаём простой вопрос:

**«Чем вы занимаетесь?»**

Он пишет естественным языком, например:

- «перетягиваю рули кожей»;
- «ставлю входные и межкомнатные двери»;
- «чиню стиральные и посудомоечные машины»;
- «реставрирую старые диваны».

Система:

1. нормализует текст;
2. ищет точные/нечёткие совпадения в `business_phrases`;
3. собирает лучшие кандидаты;
4. при необходимости передаёт исходную фразу + кандидатов AI-классификатору;
5. AI выбирает **только существующую category + variation**;
6. сохраняется confidence и источник решения;
7. при низкой уверенности пользователю показываются 2–3 понятных варианта для подтверждения.

### Жёсткое ограничение AI

AI **НЕ МОЖЕТ**:

- создавать новую категорию;
- создавать новую variation;
- придумывать новый экран;
- придумывать новую бизнес-логику;
- менять обязательность телефона;
- самостоятельно рассчитывать цену.

AI только сопоставляет человеческое описание бизнеса с фиксированной таксономией.

Рекомендуемая таблица:

```text
business_phrases
- id
- category_id
- variation_id
- locale
- phrase
- normalized_phrase
- weight
- enabled
```

Полезно также логировать:

```text
business_classifications
- id
- tenant_id
- original_text
- normalized_text
- category_id
- variation_id
- confidence
- source (exact/fuzzy/ai/manual)
- ai_model
- confirmed_by_user_at
- created_at
```

# 14. Фиксированная таксономия v1

Архитектура должна поддерживать данные в БД, но **v1 работает с фиксированным набором категорий и вариаций**. Новая профессия всё равно должна попадать в одну из существующих схем.

## 1. 🚗 Автомобили и автосервис

### A. Внешнее повреждение
Общий вид + фото повреждения.

### B. Салон / элементы автомобиля
Фото элемента + крупные планы + пожелания.

### C. Неисправность
Марка/модель + фото
