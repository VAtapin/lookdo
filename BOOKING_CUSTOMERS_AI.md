# LOOKDO — Booking, Customers, Communication & AI

> Дополнение к Части 2. Это **общие capability-модули LOOKDO**, а не отдельная логика конкретной профессии и не отдельный frontend.

Документ расширяет `CODEX.md`, но не заменяет `TEMPLATE_SYSTEM.md` и `templates/BASE_REQUEST_TEMPLATE.md`.

Главное правило: **новая профессия не получает свою систему календаря, клиентов, сообщений или AI.** Все механизмы ниже едины для всех tenant. Конкретный `request_template` только включает нужные возможности и задаёт их конфигурацию/тексты там, где это разрешено.

---

## 1. Цель

LOOKDO должен поддерживать не только сценарий «клиент показывает задачу → мастер отвечает», но и виды бизнеса, где основной следующий шаг — **запись на услугу/Termin**.

При этом LOOKDO не превращается в тяжёлую CRM.

Новые общие модули:

1. услуги;
2. рабочее расписание и календарь;
3. онлайн-запись без регистрации конечного клиента;
4. лёгкая карточка клиента и история посещений;
5. автоматические сервисные напоминания;
6. повторное приглашение клиента;
7. заполнение освободившихся окон;
8. группы/сегменты клиентов;
9. Viber / WhatsApp / Telegram и другие communication adapters;
10. AI-помощник для сообщений, ежедневных действий и публикаций;
11. AI/vision обработка фото «До/После» без изменения реального результата работы.

Все данные строго `tenant-scoped`.

---

# 2. Два универсальных входных сценария

LOOKDO должен поддерживать два общих сценария, которые могут использоваться tenant одновременно.

## A. Request flow

Существующее ядро:

**фото/видео → минимальные поля → обязательный телефон → заявка → ответ → Messages**.

Этот flow остаётся согласно `templates/BASE_REQUEST_TEMPLATE.md`.

## B. Booking flow

Новый общий flow:

**услуга → свободная дата → свободное время → имя → обязательный телефон → подтверждение записи**.

Дополнительно, если конфигурация услуги это допускает:

- короткий комментарий;
- фото;
- выбор сотрудника/мастера;
- предпочтительный канал связи.

**Регистрация конечного клиента не требуется.**

Request и Booking — два capability-flow одной платформы, а не два разных приложения.

---

# 3. Услуги

Tenant может создавать услуги.

Минимальная модель:

```text
services
- id
- tenant_id
- name
- description nullable
- duration_minutes
- price nullable
- currency nullable
- repeat_after_days nullable
- booking_enabled
- media_allowed
- active
- sort_order
- created_at
- updated_at
```

Цена здесь является ценой явно заданной услуги tenant. Это **не нарушает запрет на автоматический расчёт цены сложной заявки** из `CODEX.md`.

Для request-based бизнеса цена может отсутствовать полностью.

---

# 4. Рабочее время и календарь

У tenant появляется общий календарь.

Нужно поддержать:

- рабочие дни недели;
- часы начала/окончания работы;
- перерывы;
- индивидуальные исключения;
- выходные;
- отпуск;
- вручную заблокированные интервалы;
- длительность услуг;
- optional buffer до/после услуги;
- несколько сотрудников/мастеров в тарифах, где это разрешено.

Свободные слоты рассчитываются backend на основании:

1. расписания;
2. длительности выбранной услуги;
3. существующих записей;
4. блокировок/исключений;
5. optional buffer.

Нельзя допускать двойное бронирование одного ресурса/мастера.

Tenant Admin должен иметь простые представления:

- Сегодня;
- Неделя;
- Календарь.

Mobile-first обязателен.

---

# 5. Appointment / Termin

Минимальная модель:

```text
appointments
- id
- tenant_id
- service_id
- customer_id
- staff_user_id nullable
- starts_at
- ends_at
- status
- customer_comment nullable
- preferred_reply_channel nullable
- confirmed_at nullable
- cancelled_at nullable
- cancellation_reason nullable
- created_at
- updated_at
```

Минимальные статусы:

- `pending`
- `confirmed`
- `completed`
- `cancelled_by_customer`
- `cancelled_by_tenant`
- `no_show`

Не раздувать статусы без практической необходимости.

---

# 6. Публичная онлайн-запись

Клиент нажимает CTA типа **«Записаться» / «Termin buchen»**.

Flow:

1. выбрать услугу;
2. при необходимости выбрать мастера;
3. выбрать дату;
4. выбрать только реально свободный слот;
5. ввести имя;
6. ввести **обязательный телефон**;
7. выбрать/подтвердить предпочтительный канал связи;
8. optional комментарий/фото;
9. подтвердить запись.

Никакой регистрации, пароля или личного кабинета конечного клиента в стандартном flow.

После успешной записи:

- слот блокируется;
- создаётся/обновляется customer;
- клиент получает подтверждение;
- tenant получает уведомление;
- клиенту можно предложить service push.

Перенос записи должен показывать новые свободные слоты и атомарно освобождать старый только после успешного выбора нового.

---

# 7. Лёгкая база клиентов

LOOKDO не должен становиться CRM, но общая сущность `customer` необходима для повторных обращений, записей и коммуникации.

```text
customers
- id
- tenant_id
- name nullable
- phone
- preferred_locale nullable
- preferred_channel nullable
- marketing_consent_at nullable
- marketing_consent_source nullable
- last_activity_at nullable
- created_at
- updated_at
```

Дополнительно связи:

- requests;
- appointments;
- messages;
- media/Before-After, если это разрешено и связано с клиентом;
- tenant-private notes;
- customer groups/segments.

Основной идентификатор конечного клиента для v1 — нормализованный телефон внутри tenant.

Tenant видит в карточке клиента минимум:

- имя;
- телефон;
- язык;
- предпочтительный канал;
- последнюю услугу/заявку;
- историю записей;
- связанные фото;
- короткие внутренние заметки.

---

# 8. Напоминания о записи

Для appointments нужен общий reminder engine.

Tenant может настроить, например:

- за 24 часа;
- за 2 часа.

Система должна поддерживать несколько reminder rules, но иметь разумные defaults.

Сервисное сообщение может содержать:

- имя клиента;
- услугу;
- дату/время;
- имя мастера, если применимо;
- адрес/маршрут;
- действия **Подтвердить / Перенести / Отменить**.

Напоминания о существующей записи считаются сервисными сообщениями и должны храниться отдельно от marketing consent.

Все отправки должны логироваться с результатом доставки/ошибкой там, где provider API возвращает такой статус.

---

# 9. Повторный визит

У услуги может быть `repeat_after_days`.

Примеры:

- 28 дней;
- 35 дней;
- 90 дней.

После завершённой записи LOOKDO рассчитывает рекомендуемую дату следующего контакта.

На главном экране tenant показывать действие:

**«N клиентам пора предложить повторную запись»**.

Режимы:

1. только предложение мастеру;
2. массовое подтверждение мастером;
3. автоматическая отправка — только если tenant сознательно включил её и для конкретного канала/типа сообщения есть необходимое согласие.

AI может персонализировать текст, но не должен выдумывать услуги, скидки, цены или факты, которых нет в данных tenant.

---

# 10. Освободившееся окно

При отмене appointment слот снова становится доступным.

В Tenant App появляется действие:

**«Заполнить свободное окно»**.

Мастер выбирает слот/услугу, после чего LOOKDO:

1. находит подходящий внутренний сегмент клиентов;
2. предлагает текст;
3. при необходимости создаёт простую branded image/card;
4. предлагает доступные каналы публикации/отправки;
5. формирует deep link прямо на booking этого слота/услуги.

Как только слот занят, booking link больше не должен позволять занять то же время.

---

# 11. Группы и сегменты клиентов

Нужны два типа.

## Ручные группы

Мастер сам создаёт группу и добавляет клиентов.

Примеры:

- Постоянные;
- VIP;
- конкретная локальная группа.

## Динамические сегменты

Формируются правилами:

- давно не были;
- пользовались конкретной услугой;
- пора повторить услугу;
- предпочитаемый язык;
- предпочитаемый канал;
- новый клиент;
- постоянный клиент;
- клиенты конкретного мастера.

Один клиент может входить в несколько групп/сегментов.

**Не путать внутренний сегмент LOOKDO с группой/каналом внутри Viber, WhatsApp или Telegram.** Публикация во внешнюю группу/канал возможна только если конкретная интеграция и права API это позволяют.

---

# 12. Communication adapters

Сообщения и уведомления должны идти через общий abstraction layer.

Приоритетные каналы:

- Web Push/PWA;
- Telegram;
- Viber;
- WhatsApp;
- e-mail владельца tenant;
- позже SMS при необходимости.

Не писать Viber/WhatsApp/Telegram-логику прямо в booking service.

Концептуально:

```text
CommunicationService
  -> WebPushAdapter
  -> TelegramAdapter
  -> ViberAdapter
  -> WhatsAppAdapter
  -> EmailAdapter
```

Каждый adapter обязан учитывать реальные возможности, разрешения и ограничения API провайдера.

Если provider не позволяет автоматическую отправку конкретного типа сообщения, LOOKDO должен уметь:

- подготовить текст;
- подготовить изображение;
- создать deep/share link;
- открыть соответствующее приложение;
- не изображать успешную автоматическую отправку, которой не было.

---

# 13. AI-помощник коммуникаций

AI здесь имеет другую роль, чем AI-классификатор onboarding.

Он может:

- подготовить сервисное сообщение;
- персонализировать разрешённое сообщение по имени/услуге/дате;
- перевести сообщение на язык клиента;
- подготовить приглашение на повторный визит;
- подготовить публикацию о свободном окне;
- написать короткий текст к работе/Before-After;
- предложить CTA;
- подготовить 2–3 коротких варианта текста мастеру на выбор.

AI должен получать только необходимые tenant/customer данные и не должен придумывать:

- несуществующую услугу;
- несуществующую скидку;
- цену, которой нет в данных;
- свободный слот без проверки календаря;
- факт посещения, которого нет в истории;
- медицинские/профессиональные обещания, которых tenant не задавал.

Финальная проверка доступности слота всегда выполняется обычной backend-логикой, не AI.

---

# 14. AI-помощник действий / умный главный экран

Tenant Admin должен показывать не только статистику, а практические действия.

Пример:

```text
Сегодня 5 записей
13:00–14:30 свободно
2 записи ещё не подтверждены
8 клиентам пора предложить повторный визит
3 новые работы ещё не опубликованы
```

Действия:

- Напомнить;
- Заполнить окно;
- Пригласить клиентов;
- Создать публикацию;
- Проверить неподтверждённые записи.

AI может ранжировать и формулировать рекомендации, но все действия должны основываться на реальных данных LOOKDO.

Никакой автономной отправки массовых сообщений без явно включённого режима и необходимых consent/permissions.

---

# 15. AI / Vision для фото «До/После»

Нужен общий media-processing pipeline.

Цель — не изменить результат работы, а сделать пару фотографий визуально сопоставимой.

Разрешённые операции:

- определить главный объект/область;
- определить landmarks, если применимо;
- выровнять наклон;
- привести изображения к одинаковому масштабу;
- одинаково кадрировать;
- центрировать;
- аккуратно нормализовать экспозицию/баланс белого;
- создать пару/коллаж «До / После»;
- создать social/publication crop;
- добавить tenant branding, название услуги, цену из данных и booking link/QR.

### Жёсткое правило достоверности

Для portfolio/Before-After AI **не должен генеративно менять сам результат работы**.

Нельзя:

- дорисовывать или удалять реальные дефекты;
- улучшать выполненную мастером работу так, будто результат был другим;
- добавлять детали, которых не было на фотографии;
- менять форму объекта/лица/бровей ради более эффектного результата.

Допускаются только композиционные и технические коррекции, сохраняющие фактический результат.

Профиль конкретной профессии может задавать правила анализа, например landmarks лица/глаз для beauty, но это конфигурация processing profile, а не отдельный frontend.

---

# 16. AI-публикации

Из существующей работы/Before-After мастер нажимает **«Создать публикацию»**.

LOOKDO подготавливает:

- изображение;
- короткий заголовок;
- текст;
- CTA;
- цену только если она явно задана;
- booking/request link;
- нужный язык.

Форматы минимум:

- Story;
- square/standard post;
- share card для Viber/WhatsApp/Telegram.

Мастер может отредактировать результат перед публикацией.

---

# 17. Локализация

Platform UI по-прежнему обязан поддерживать базовые локали проекта.

Архитектура customer communication и tenant content не должна быть ограничена только тремя platform locales. Нужно предусмотреть подключаемые tenant/customer locales, например `uk`, без создания нового frontend.

Хранить у customer `preferred_locale`.

AI-перевод не заменяет системные локализации критических UI-текстов, но может использоваться для tenant-authored communication drafts.

---

# 18. Consent и разделение сервисных/маркетинговых сообщений

Обязательно различать:

## Service communication

- подтверждение записи;
- напоминание;
- перенос;
- отмена;
- ответ по существующей заявке;
- важное изменение существующей записи.

## Marketing / re-engagement

- массовая реклама;
- приглашение давно неактивных клиентов;
- promotional рассылка;
- публикации/рассылки о свободных окнах конкретным клиентам, если по применимым правилам это marketing.

Согласие на marketing хранить отдельно и доказуемо.

Не использовать согласие на service push как согласие на рекламу.

---

# 19. Entitlements

Новые возможности должны проходить через существующий entitlement service, а не hardcode в Vue.

Предусмотреть keys, например:

```text
booking_enabled
calendar_enabled
customer_history_enabled
reminders_enabled
repeat_visit_enabled
customer_segments_enabled
whatsapp_integration
viber_integration
telegram_integration
ai_messages_enabled
ai_media_enabled
ai_publications_enabled
staff_calendar_limit
```

Точные тарифные значения задаются через Super Admin/plan entitlements и не фиксируются в этом документе.

---

# 20. UI и простота

Новые функции не должны превращать Tenant Admin в тяжёлую CRM.

Mobile-first навигация должна сводиться к реальным действиям мастера.

Для бизнеса с booking функционалом приоритетные рабочие состояния:

- Сегодня;
- Календарь;
- Клиенты;
- Сообщения;
- Контент/Работы.

Дополнительные настройки могут находиться глубже.

Публичное Tenant App также не должно получать длинную навигацию. Booking может быть основным CTA или contextual action в рамках общей app-структуры.

---

# 21. Архитектурное правило для шаблонов

`request_template` **не реализует** календарь, customer database, reminders, communication adapters или AI pipeline.

Шаблон может только конфигурировать использование общих capabilities, например концептуально:

```json
{
  "capabilities": {
    "request": true,
    "booking": true,
    "before_after": true,
    "reviews": true,
    "repeat_visit": true,
    "ai_media_profile": "face-landmarks"
  }
}
```

Набор допустимых capability keys централизован и валидируется backend.

Если новый вид бизнеса требует уже существующую capability — включается конфигурация.

Если действительно нужен новый универсальный механизм — он сначала добавляется в ядро LOOKDO, а не внутрь одного шаблона.

# 22. Рекомендуемый порядок реализации в Части 2

1. базовые customers как связь requests/appointments/messages;
2. services;
3. availability/calendar engine;
4. booking flow;
5. appointment reminders;
6. reschedule/cancel/confirm flow;
7. repeat-visit engine;
8. customer groups/segments;
9. unified CommunicationService + adapters;
10. AI communication drafts;
11. Before/After normalization pipeline;
12. AI publication generation;
13. smart action dashboard;
14. staff/multi-resource calendar расширять после стабильного single-master flow.

Сначала сделать надёжный single-master booking, потом усложнять.

# 23. Критерий правильной реализации

Функциональность считается правильно встроенной в LOOKDO, если:

- один booking/calendar engine обслуживает разные виды бизнеса;
- конечному клиенту не нужна регистрация;
- телефон остаётся надёжным обязательным контактом;
- template не создаёт специализированный booking frontend;
- reminders и communication используют общий adapter layer;
- AI не принимает решения вместо календаря/backend;
- AI не фальсифицирует Before/After;
- marketing и service communication разделены;
- новый beauty/repair/consulting template может подключить эти возможности конфигурацией без копирования логики.
